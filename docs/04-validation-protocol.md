## 2. 为什么要先做这一小步

只做前向计算，模型可以给出数值，却不能证明梯度、优化器和保存流程正确。直接扩大数据，可能在运行很久后才发现这些问题。固定一个样本和两次更新，使问题容易定位，资源占用也有明确上限。

同一条训练样本上的 loss 只能说明拟合过程。两次更新不保证 loss 单调下降；loss 下降也不能替代未见场景上的任务成功率。

## 3. 使用共享 GPU 的启动条件

服务器常规检查间隔为 **7,200 秒，即两小时**。只有可能满足启动条件时，才进行短间隔的连续复查。空闲发生在两次常规检查之间时，需要等到下次计划检查才会发现。

启动前要求原占用任务退出、没有其他 GPU 计算进程，并连续满足 GPU 低利用率、足够空闲显存和主机可用内存。当前脚本采用空闲显存至少 27GiB、主机可用内存至少 32GiB 的保守阈值；这些是本次脚本限制，不是作者公布的通用最低配置。

后台任务已取得脱离 SSH 的运行回执。Windows 锁屏或 SSH 断开本身不会终止这个独立服务器进程，但仍可能有服务器重启、程序错误或监测到期等情况，需要靠真实状态判断。

监测窗口为一次约 24 小时的等待；部署时记录的截止时刻为 **2026-10-18 12:13:13 北京时间**。到期不自动延长。当前文档不能证明截止时刻之后任务已结束或已成功。

## 4. 为什么最多尝试一次

启动器在提交训练前持久写入一次性标记，训练入口另有执行标记和锁。存在标记意味着必须先调查已有结果，不能删除标记再重新训练。

即使启动后报错、超时或结果缺失，本次机会也可能已经消耗。避免因为网络断线、界面旧输出或重复请求而启动多个训练进程。此机制是避免重复运行的保护，不表示在共享机器上获得了排他调度权。

本次训练尝试外部限时 **300 秒**，必要时再给约 15 秒清理其自身进程组。300 秒是尝试上限，不是已经测得的完成耗时。失败后的修复和重新运行需要结合日志重新确定，不能自动扩展成全量训练。

## 5. 成功必须看到哪些证据

| 核查项 | 成功标准 | 不能代替什么 |
|---|---|---|
| 实际训练步 | 日志或结果记录恰好 2 次更新 | 只启动进程不算完成 |
| 数值 | 两次 loss 均为有限值 | 不保证 loss 下降或策略更好 |
| 参数更新 | 被探测的 LoRA 参数发生有限变化 | 不能仅以有梯度字段判断学到了技能 |
| 检查点 | 所需文件齐备，格式与阶段正确 | 有一个目录不算保存成功 |
| 严格读回 | 官方加载器在同一模型实例上读回，探测参数精确相等 | 不等于全新进程恢复推理已验证 |
| 阶段属性 | `decoder_trained=false` 得到保留 | 不能把输出当作已训练动作策略 |
| 资源记录 | 保存本次实际训练显存峰值、耗时和退出状态 | 前向峰值不能代替训练峰值 |

当前脚本的检查点读回是**同一实例上的严格加载验证**；`reload_forward_tested=false`。未来仍需单独验证新进程加载、输入预处理一致性和推理输出，不能提前写成“完整保存重载推理通过”。
